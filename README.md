# Лабораторная работа 3 — порядковый номер 5

**C++17 + Go**, многофайловые проекты по структуре присланного примера.
Дерево — **Complete Binary Tree из личной ЛР1 (вариант дерева 3)**.
Теория — **нечётный вариант: российские стандарты оценки качества ПО**.
Порядковый номер 5 не меняет закреплённый в ЛР1 вариант дерева 3.

## Что готово

- Массив, односвязный и двусвязный списки, стек, очередь, Complete Binary Tree.
- Хеш-таблица с двумя режимами из ЛР2: линейное пробирование и двойное хеширование.
- Закрытые поля и открытые операции; C++ RAII и независимое копирование объектов.
- Общий виртуальный интерфейс Serializable в C++; интерфейс Serializer в Go.
- Бинарная **и** текстовая сериализация каждой структуры в обоих проектах.
- Настоящие Google Test, Boost.Test, Catch2; Go testing + testify.
- Benchmark-тесты Google Benchmark и testing.B.
- Статический анализ Clang, cpplint, go vet, проверка gofmt.
- HTML-покрытие, UML-диаграммы, PDF-отчёт, исходник отчёта Markdown.

Готовые результаты открываются без сборки: **[reports/index.html](reports/index.html)**.
Основной отчёт: **[docs/REPORT.pdf](docs/REPORT.pdf)**.

## Быстрый запуск

Нужны CMake 3.20+, Clang с поддержкой C++17, Go 1.22+, Python 3.9+.
Для линтера C++: `python3 -m pip install cpplint==2.0.2`.
CMake при первой сборке скачивает закреплённые Google Test, Catch2, Boost и Google Benchmark.
Это требует доступа к интернету; исходники тестовых библиотек и сборочные файлы
не включены в архив. Зависимости Go уже включены в `golang/vendor/`.

Из корня папки:

```sh
cmake -S . -B build -DCMAKE_CXX_COMPILER=clang++ -DLAB3_COVERAGE=ON
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
cd golang
go test ./... -count=1
go run ./cmd/lab3 --demo ../examples/go
cd ..
./build/lab3 --demo examples/cpp
```

На macOS компилятор и LLVM-инструменты доступны через Xcode Command Line Tools.
На Linux для HTML-покрытия нужны `llvm-cov` и `llvm-profdata`, соответствующие
версии Clang, которой собран проект. При проблеме `-DCMAKE_CXX_COMPILER`
можно указать полный путь к нужному Clang.
На Windows используйте CMake/Clang и команды напрямую; Makefile рассчитан на
macOS/Linux. Отдельно на Windows/Linux проект не запускался.

При наличии Make:

```sh
make verify   # тесты, HTML-покрытие >=85%, анализаторы и обмен C++ <-> Go
make bench    # benchmark-тесты обеих версий
make demo     # примеры файлов
```

Каждый шаг можно выполнить отдельно:

```sh
python3 scripts/coverage.py --build build
make coverage-go
python3 scripts/lint.py
cd golang && go test -race ./ds
```

`make verify` проверяет порог для каждого Go-файла с операторами и для каждого
из трёх C++-наборов. Метрики относятся ко **всей библиотеке структур и сериализации**
(`str/`, `golang/ds/`), включая обработку ошибок. Тесты, сторонние библиотеки,
benchmark-код и демонстрационные CLI в знаменатель не входят.
В C++ измеряется покрытие строк, в Go — операторов; это разные метрики.

## Демонстрация сериализации

Создать по два файла для каждой из 8 структур/режимов:

```sh
./build/lab3 --demo examples/cpp
cd golang
go run ./cmd/lab3 --demo ../examples/go
```

Перевод файла из одного формата в другой:

```sh
./build/lab3 --convert Array text examples/cpp/Array.txt binary array.bin
./build/lab3 --convert Array binary array.bin text array.txt
```

Аналогичный интерфейс Go:

```sh
cd golang
go run ./cmd/lab3 --convert Array binary ../array.bin text ../array-go.txt
```

Типы: `Array`, `OneLinked`, `Linked`, `Stack`, `Queue`, `OpenHash`, `LinearHash`, `Tree`.
`OpenHash` — двойное хеширование, `LinearHash` — линейное пробирование;
это два режима одного класса, а не разные алгоритмы деревьев.
Полное описание форматов — [docs/FORMATS.md](docs/FORMATS.md).

## Поведение структур

- Пустые pop/top/front и неверные индексы: исключение C++ или ошибка Go.
- Вставка до/после ключа использует **первое** совпадение; отсутствующий ключ — ошибка.
- Удаление отсутствующего значения возвращает false.
- Дубликаты разрешены в списках и дереве, но не в хеш-множестве.
- Complete Tree вставляет по уровням слева направо, ищет обходом в ширину,
  проверяет полноту. **Это не BST и не AVL.** Удаление дерева не добавляется:
  в личной ЛР1 оно заменено проверкой полноты.
- Поля Go со строчной буквы скрыты от других пакетов, а не от других файлов
  того же пакета. Это эквивалент инкапсуляции на уровне пакета, не C++ private.
- Копирование Go-контейнеров с внутренними ссылками делайте через Clone;
  обычное присваивание структуры может разделять узлы/массивы.
- Объём массива и хеш-таблицы ограничен 65536 ячейками как в примере;
  загрузка таблицы контролируется порогом 70%. Числа дерева — int32.
- Порядок обхода хеш-таблицы не является частью контракта. После сериализации
  сохраняются множество ключей и метод пробирования; порядок размещения может измениться.
- Повреждённый ввод не заменяет существующий объект: загрузка сначала создаёт временное состояние.

## Связь с личными ЛР1 и ЛР2

Алгоритмы линейных структур и Complete Tree перенесены в объектную модель
из предоставленной личной ЛР1. Правила пробирования, метки удаления, рост таблицы
и множество соответствуют личной ЛР2. Названия классов и организация тестов
сохранены близкими к GitHub-примеру ЛР3. Подробнее — [SOURCE.md](SOURCE.md).

ЛР3 требует переработать **структуры данных**, поэтому задачи про геномы,
ударения и сотрудников из ЛР2 здесь повторно не выдаются как отдельные задания.
В отчёте показана преемственность структур, на которых они работают.

## Результаты и навигация

- `reports/gtest/`, `reports/boost/`, `reports/catch2/`: HTML-покрытие, XML и журналы тестов.
- `reports/go/`: HTML-покрытие, исходный профиль, результаты тестов и benchmark-тестов.

- `reports/cpp_analyzer.txt`, `cpplint.txt`, `lint.txt`: результаты статических проверок.
- `reports/cpp_ubsan.txt`: дополнительная проверка UndefinedBehaviorSanitizer.
- `docs/REPORT.pdf`, `REPORT.md`: отчёт и редактируемый текст.
- `docs/uml_*.mmd`, `uml_*.svg`: исходники UML и готовые диаграммы.

Встроенные HTML-отчёты — снимок реально проведённого запуска. Чтобы получить
новые результаты после изменения кода, повторите команды проверки.
